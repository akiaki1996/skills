# design-scope — 设计收敛与审计文档

feature 开发最初期的设计探索 skill。输入是用户的碎碎念/半成品想法，输出是一份完整详细、可供审计的设计文档——记录从"模糊想法"到"确定方案"的完整轨迹。

## 这个 skill 在流水线里的位置

```
碎碎念 → [design-scope: 多轮提问收敛] → 设计文档 → [write-spec: 实施 spec] → [write-plan: 施工图] → [implement-plan]
```

- **design-scope 回答**："这个 feature 到底做什么、怎么实现、怎么接入现有系统、为什么这么做"
- **不是实施 spec**：不写完整实施细节、不写逐步 Task——那些是 write-spec / write-plan 的职责
- **审计性**：文档必须能回答"当时为什么这么定"，所以记录每轮问答演变与每个被否方案

## 触发时机

- 用户抛出一段碎碎念/半成品想法，说"我们聊聊""帮我理清""确定一下方案"
- 用户说"用 design-scope 收敛一下这个想法"
- 典型输入长这样（用户可能直接粘贴）：

  > 我在考虑一个设计实现，希望我们先经过多轮互动确定这个 feature 如何实现和接入，然后再把它整理为一个完整详细可供审计的设计文档，这里有一些我的初始碎片化想法：
  > - [碎碎念 1]
  > - [碎碎念 2]

## 执行流程

### Phase 0：理解初始想法 + 现状盘点

1. 读用户的碎碎念。用 3-5 句话复述你的理解（做什么、可能的形态），确认大方向没跑偏
2. **盘点现有系统**（写任何方案前必做，防重复造轮子）：
   - 相关模块/文件在哪、现有实现做到什么程度
   - 这个 feature 可能的接入点（哪个模块、哪个接口、数据从哪来去哪）
   - 项目惯例（CLAUDE.md / 测试命令 / 目录结构）
3. 把盘点结果摆给用户看（简要），尤其指出发现的现有轮子和相关代码

### Phase 1：Socratic 多轮提问迭代

**节奏**：每轮 2-4 个聚焦问题，基于上一轮回答深挖，逐轮逼近收敛。**一次不问超过 4 个**。

**每轮的结构**：
1. 「当前理解快照」——已收敛的点 + 仍开放的点用 Bullet 列出（让用户随时纠偏）
2. 本轮 2-4 个聚焦问题（具体、指向一个可决定的选项，不写"你怎么看"式开放题）

**问询维度**（按此优先级推进，不必每轮都触及全部）：

| 维度 | 要收敛的问题 |
|------|------------|
| 目标与动机 | 做什么？为什么现在做？不做会怎样？成功长什么样？ |
| 场景与用户 | 谁在用、什么场景、现状怎么绕过这个需求？ |
| 接入点 | 挂在哪、数据流从哪进哪出、和现有模块怎么交互 |
| 方案取舍 | 候选方案有哪些、为什么选这个、被否的方案什么理由 |
| 边界 | 明确不做什么（YAGNI）、范围红线 |
| 验收 | 怎么证明做对了（可判真假，不写"工作正常"） |
| 风险 | 约束、兼容性、受保护代码、回退路径 |

**深挖技巧**：
- 每个答法都追问一步"为什么"或"如果……会怎样"，直到底下没有开放决策
- 用户说"随便""你定"时，给出你的推荐 + 理由，让用户确认而非直接略过
- 发现方案有硬伤时明确说出来（指出冲突 > 迎合），把矛盾摆到台面上解决

### Phase 2：收敛判定

满足以下全部条件才判定收敛，主动提议落笔：

- 目标与动机明确（知道为什么做、不做什么）
- 方案已选定（含被否方案的理由）
- 接入点确定（挂哪、数据流清晰）
- 边界清晰（YAGNI 列表）
- 验收标准可判真假
- 风险已知（含受保护代码检查）

**收敛不足的典型信号**：还有"到时候再说""可能也行"的决策点。继续问，不落笔。

### Phase 3：落笔 — 产出审计设计文档

落笔前快速扫项目惯例确定文档目录（沿用已有 design/spec 目录惯例；否则默认 `docs/designs/`）。

创建 `docs/designs/YYYY-MM-DD-<slug>-design.md`，按固定结构写入：

```markdown
# <功能> 设计文档

**日期**：YYYY-MM-DD
**状态**：已收敛 / 待审
**关联**：<相关 issue / 上游文档>

## 0. 背景与动机
为什么做、为什么现在做、不做的代价

## 1. 需求演变轨迹（审计核心）
- **1.1 初始想法**：用户的碎碎念原文（不改写）
- **1.2 问答演变**：每轮 Q/A 摘要 + 当场达成的小决策
- **1.3 关键分歧与裁定**：有冲突的点、为什么最终这么定

## 2. 现状盘点
- 现有相关模块/轮子（文件路径）
- 本次要补的缺口
- 接入点分析

## 3. 最终设计方案
- 整体思路（一句话）+ 为什么这样切
- 数据流（ASCII 图）
- 接口/接入方式（骨架级签名，不写完整实现体）
- 影响面盘点（✅ 不改 / ⚠️ 改但 surgical / 🔴 大改）

## 4. 被否方案与理由
每条：方案是什么 → 为什么否 → 什么条件下会重新考虑

## 5. 验收标准
编号列表，可判真假，绑定真实测试/观测手段

## 6. 风险与注意事项
约束、兼容性、受保护代码、回退路径

## 7. YAGNI / 明确不做的
防实施 agent 多做

## 8. 开放问题（若有）
未决事项，标注"待决"，并在文档头部状态注明

## 9. 后续衔接
- 下一步：write-spec 出实施 spec → write-plan 出施工图
- 或直接进入实施的条件
```

### Phase 4：收尾

- 汇报文档路径 + 一句话总结收敛结果
- 提醒：设计确认后可用 write-spec 落实施 spec

## 必做的交叉检查

### 1. 现状盘点先于提方案

写任何方案前先 grep/ls 项目，防重复造轮子。发现已有实现 → 摆出来让用户决定"复用还是重写"。

### 2. 审计真实性

- 演变轨迹只记录本轮问答实际发生的，不事后编造"当时考虑过 X"
- 每条被否方案有真实理由，不凑数

### 3. 验收标准可判真假

不写"工作正常""性能好"，写"跑 X 命令输出 Y"类可验证表述（照项目真实手段）。

### 4. 受保护代码检查

改动触及 vendored / 自动生成 / CLAUDE.md 声明的受保护代码时，在「6. 风险」注明 surgical 守护（逐处编辑、不整文件覆盖）。

### 5. Socratic 纪律

- 每轮 ≤4 个问题
- 展示「理解快照」后再问，让用户能纠偏
- 收敛不足不落笔

## 产出

```
docs/designs/YYYY-MM-DD-<slug>-design.md
```

`<slug>` 是功能名 kebab-case 缩写。写完后提示用户：设计已收敛，确认后可用 write-spec 出实施 spec。
