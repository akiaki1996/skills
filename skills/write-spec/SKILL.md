# write-spec — 设计 spec 写入

将设计 session 的讨论收敛成一份**设计说明**文档，写入 `docs/specs/YYYY-MM-DD-<slug>-spec.md`。

## spec 是什么、不是什么

- **spec = 功能/设计说明**：回答"做什么、为什么这么做"。给人审阅、给实施 agent 建立背景理解。
- **spec 不是施工图**：不含完整可复制运行的代码、不含逐步 Task。那些是 **plan** 的职责（`write-plan`）。spec 里代码**只到骨架/签名/关键片段级**，说清意图即可。
- **SSOT**：完整实现代码只存在于 plan，不在 spec 重复。spec 说"要把 X 改成支持 Y"，plan 才给"X 的完整新代码"。

## 触发条件

- 在设计 session 中跟用户讨论设计，方向已明确
- 用户说"写 spec""落笔""写设计文档"或类似表述
- agent 自己判断讨论已收敛、可以写 spec 了（主动提议）

## 落笔前：读一遍项目惯例

在写之前，快速扫一遍当前项目，让 spec 贴合本项目而非泛泛而谈：

- **项目约定文档**：`CLAUDE.md` / `AGENTS.md` / `README` / `CONTRIBUTING`——测试命令、目录结构、编码规范、受保护区域
- **spec 存放惯例**：项目里已有 spec/design 文档吗？在哪个目录、什么命名？沿用它（否则用默认 `docs/specs/`）
- **构建/测试入口**：`Makefile` / `package.json` / `pyproject.toml` / `justfile`——本项目怎么跑测试和 lint（供「验收标准」段引用真实命令）

## Spec 文档的固定结构

创建文件 `docs/specs/YYYY-MM-DD-<slug>-spec.md`（若项目另有 spec 目录惯例则沿用），按以下结构写入。

### 标题 + 元信息

```markdown
# <功能短描述> 设计 spec

**日期**：YYYY-MM-DD
**状态**：待审批 / 已审批 / 待执行
**关联**：<上游 handoff / spec / issue / PR 链接，若有>
```

### 1. 问题定义与根因

- **1.x 症状**：当前哪里不对、观察到什么现象
- **1.x 证据**：逐行日志 / 复现步骤 / 实测结果（有则贴），不靠"我觉得"
- **1.x 为什么**：根因分析——是架构问题还是措辞/配置问题，往下挖到可动手的那一层

### 2. 当前已有什么

盘点现状，**防重复造轮子**：

- 相关的模块 / 工具 / 函数 / 库已经存在哪些？在哪个文件？
- 现有实现做到了什么、缺了什么（本次要补的）
- 项目依赖或框架里有没有现成能复用的机制（先查再造）

> 若确认无现成可复用，明写"无现成实现，需新增"——让审阅者能否决"其实有轮子"。

### 3. 设计方案

- **3.x 整体思路**：一句话方案 + 为什么这样切
- **数据流**：用 ASCII 流程图表示从输入到输出的完整路径
- **接口/schema**：输入什么、输出什么（骨架级，如函数签名、数据结构），**不写完整实现体**
- **关键代码片段**：只在"必须靠代码才说得清意图"处贴骨架，标注"骨架，完整实现见 plan"
- **影响面盘点**：这个改动会碰到哪些模块/层次（前端/后端/数据/接口/配置……按本项目结构列）。每处标注：✅ 不改 / ⚠️ 改但 surgical / 🔴 大改

### 4. 验收标准

编号列表，每条可验证。**implement-plan 收尾的 code-review 会逐条对照此列表**（spec-fidelity 轴），所以要写成"能判真假"的形式，不写"工作正常"这种模糊标准。尽量绑定到本项目的真实验证方式（测试命令、可观测产物）。

### 5. 风险与注意事项

- **约束**：行为不变约束（重构类）、性能/安全/兼容性约束
- **边界（YAGNI）**：明确列出**不做的**，每条一条——防实施 agent 多做
- **受保护/上游代码**：改动是否触及 vendored / fork / 生成的上游代码或项目声明的受保护区域（查 `CLAUDE.md` / `.gitattributes` / vendor 目录）？若是 → 注明"实施时 surgical，不整文件覆盖，守护本地定制"

### （可选）设计决策 / 文件变更范围

- **设计决策**：记录"为什么这样不那样"的关键取舍
- **文件变更范围表**：`文件 | 变更类型 | 行数估计`，给审阅者规模感

## 必做的交叉检查（写 spec 时自动执行）

在生成 spec 内容之前，过一遍这些检查。命中则在对应段落注明。

### 1. 影响面盘点 → 挂进「3. 设计方案」

这个改动涉及本项目的哪些部分？按项目实际结构（读目录 / CLAUDE.md）列出受影响的模块或层次，每处标注改动幅度（✅/⚠️/🔴）。

### 2. 受保护 / 上游代码检查 → 挂进「5. 风险」

项目里有没有 vendored、fork、自动生成、或 CLAUDE.md 声明受保护的代码？改动触及它们时，注明 surgical 守护（逐处编辑、不整文件覆盖）。

### 3. 循环 / 顶层 import 风险 → 挂进「5. 风险」

改动核心模块（被广泛 import 的基础模块）时，新增 import 可能闭合导入环，导致生产入口启动失败但测试假绿。若涉及 → 注明"惰性 import，不放模块顶层" + "改后裸导入验证生产入口"。

### 4. LLM/harness 三大病理自检（若改 prompt / agent / 控制流）→ 挂进「5. 风险」

改动涉及 LLM prompt、agent 行为、guardrail、控制流时，过一遍三问：

1. **Reward hacking**：新增的 guard/validator 会不会被糊弄？→ 验收看真产物不看 LLM 自述
2. **Catastrophic forgetting**：修 A 会不会回归 B？→ grep 所有消费者，全量回归
3. **Under-exploration**：是不是在改 prompt 逃避结构改动？→ 判据：结构缺失→上结构门；结构已对只缺指引→改 prompt

（纯代码改动、不碰 LLM/agent 的，此项标 N/A。）

## 产出

生成的 spec 文件路径：

```
docs/specs/YYYY-MM-DD-<slug>-spec.md
```

其中 `<slug>` 是功能名称的 kebab-case 缩写（如 `gate-enforcement`）。

写完后提示用户：spec 已就绪，确认后可用 `write-plan` 出施工图 plan。
